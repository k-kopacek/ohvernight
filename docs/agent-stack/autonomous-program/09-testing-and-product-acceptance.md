# 09 — Acceptance contract, independent review and product value

## Minimum release gates

1. All current approved contract validators (Python/Node/browser/CI) pass on exact PR head; deterministic rebuilds match committed display artifacts; source/license checks recorded.
2. **Zero known critical trust misstatements:** false permission/open/access, weakened restriction, non-federal→private, proximity→connection, unmapped unknown presented as empty/restricted, source fetch→review, fabricated source or claim.
3. Source IDs, aliases, cross-region identities and negative/hostile fixtures pass; no data loss hidden by dedupe.
4. Existing byte, performance, memory and real-device gates remain binding until explicitly amended. A Chrome phone viewport cannot replace required Safari/iPhone owner test automatically.
5. Independent Claude implementation review at final head and separate data/source-review process where approved spec requires it; Codex self-tests never count as independent review.
6. A pre-merge checklist includes deployment blast radius, rollback and current authorization. Merges to main publish to GitHub Pages.

## User-oriented acceptance

From M5 onward and once after M4, apply `docs/product/product-scorecard.md`: SHIPPED; USER CAN NOW; USER STILL CANNOT; OUTSIDE RESEARCH STILL REQUIRED; TRUST/UNKNOWN STATE; ACCEPTANCE SCENARIO RESULT. Compare concrete planning steps, unresolved critical questions, outside apps, source freshness, unknown link counts and phone burden with the previous baseline. A milestone can improve foundations without making a usable trip; say so.

## Scenario pack

Turn target scenarios from `01-target-product.md` into stable, evidence-anchored cases plus an explicit manual phone checklist. For each case, define intent, expected candidates or coverage limitation, evidence/source IDs, type of relationship required, negative assumptions prohibited, UI steps, success/failure and date checked. Keep a small independent adversarial suite with hostile strings, stale restrictions, ambiguous road/vehicle designations and unsupported positives. No AI-generated answer key accepted without reviewer grounding.

## Mobile UX as a blocker, not a footnote

Shared sheet/header defects found on real iPhone must be fixed structurally rather than repeatedly masked with CSS offsets. A scrollable body cannot paint over a pinned header. Verify in Safari with wrapped summary, long title, collapsed/half/expanded, app switching, safe areas and source link. If a mandated owner device gate cannot be automated or delegated under approved policy, lock merge but continue building/testing other authorized tasks.

## Product end-state bar

Do not declare DONE only because M1–M8 checklist rows are marked complete. Show a statewide cross-region Explore flow and end-to-end Choose Your Adventure, with every acceptance scenario run and product scorecard vs baseline. Demonstrate at least one supported multi-component candidate and honest cases where coverage does not support one. List missing regions/evidence; statewide geographic support cannot be mislabeled statewide legal or recreation certainty.

## Final owner package

Accessible staging URL/build SHA; video/screenshots or supervised real phone test outcomes; completed scenario matrix; provenance and licensing audit; critical trust test report; performance/bytes; known gaps, unresolved questions and risk; rollback; before/after user value metrics; concise “what works/what does not” walkthrough for owner critique. No self-certified production readiness if protected gates remain pending.
