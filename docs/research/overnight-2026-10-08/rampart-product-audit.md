### Would a first-class area entity fix the failure?

An entity with `contains-trails`, `served-by-staging`, `governed-by`, `constrained-by-orders`, `accessed-via-road`, and `associated-with-family-facilities` can represent the full planning context eventually, but only if each edge carries source-backed evidence or a reviewed candidate. Creating these edges from shared wording or a buffer would encode unproven access/permission and repeat the current “nearby means connected” problem. A label-only area identity would not itself prove membership either.

Smallest search fix: an area/topic record with stable ID and name/aliases (“Rampart Range Motorized Recreation Area”, “Rampart”), whose action searches or filters the existing county-clipped trail collection and presents candidate results explicitly as “Rampart-area candidates — source membership not established.” Do not add implied membership to canonical trail features. This fixes the zero-result name search without claiming boundaries or route links; the list selection rule still needs review against a Forest Service map/source before it can be called complete.

Full M6 model, consistent with `docs/architecture/adventure-model.md`: stable user-facing trail identity distinct from member source segments; preserved member IDs; a first-class trailhead/staging identity only where source provides it; each `starts_at`/`accessed_from`, `approached_via`, `governed_by`, `constrained_by`, `served_by_staging` and family-facility association recorded with direction, stable endpoint IDs, origin (`source-backed`, `derived`, `reviewed candidate`, `unknown`), rule/evidence and review date. Unknown remains default. Topology and distance may create candidates for review but do not become published relationships. Keep trail identity across county/package boundaries; do not infer the rest of Rampart from the Douglas clip.
